# Business rule answers

Answered against the legacy `svg-gen` service's actual runtime behaviour. Where the legacy code has no observable rule for a question, that is stated.

---

### Q1 — Should the new svg-gen service require an auth token on its HTTP endpoints?

- **Should `/render` and `/image/fromQuestion` require an auth token in production?**
  The legacy `svg-gen` HTTP service ships with **no authentication on any endpoint**. `/health`, `/render`, `/image/fromQuestion`, `/test/component`, and `/test/component-tester` are all openly reachable by any caller that can reach the bound port. There is no bearer-token check, no API-key header, and no per-caller credential plumbed into the service.
- **Same shared token vs per-caller credentials?**
  Not applicable today — there is no token concept inside the legacy service.
- **Unauthenticated request response shape and message?**
  No such response exists. Every well-formed request is processed regardless of caller identity.
- **Is `/health` always reachable?**
  Yes — `/health` is an unconditional `GET` that returns `{"status": "ok"}` with HTTP 200. It performs no checks beyond confirming the process is up, so it is suitable as a Cloud Run liveness/readiness probe today.

I cannot answer what the *new* product should require — that is a forward-looking product decision and not derivable from current behaviour. The factual baseline is: the legacy service is open.

### Q2 — When the service decides a request is "not supported", what should the caller see?

Today, "not supported" is signalled differently on the two surfaces:

- **`/image/fromQuestion`**: when the upstream feasibility check decides a question cannot be rendered, the caller receives **HTTP 400** with a JSON body of the form:
  ```json
  {
    "detail": {
      "error": "UnsupportedRequest",
      "message": "Request is not supported by the deterministic SVG renderer. Fallback image generation is disabled.",
      "details": { "feasibility_reasoning": "<model-authored explanation>" }
    }
  }
  ```
  The `message` is a **fixed string**. The `feasibility_reasoning` inside `details` is **free text generated by the feasibility LLM** — it is not drawn from a fixed catalogue. There is no separate "what is supported" hint surfaced beyond that reasoning.
- **`/render`**: the `/render` endpoint does not run a feasibility check — it accepts a `SceneV1` payload directly. Two distinct rejection paths exist:
  - **Schema validation failure** → **HTTP 400** with body `{"error": "InvalidScene", "message": "Scene validation failed", "details": [<pydantic errors>]}`.
  - **Unknown component inside a valid envelope** → currently surfaces via the generic `500 InternalError` path on `/render` (the `UnknownComponent` typed mapping only takes effect via the `/image/fromQuestion` path, which routes through `AgentService`).
- **Additional status codes available on `/image/fromQuestion`**:
  - `501 NotImplemented` is reserved for the `NotImplemented` agent error type.
  - `500 InternalError` is the catch-all for unexpected exceptions.
- **Hint about what *is* supported?**
  No structured hint is returned today. Only the LLM's free-text reasoning ships back to the caller.
- **Same behaviour across `/render` and `/image/fromQuestion`?**
  No — the two endpoints behave differently. `/render` has no feasibility gate at all; it only knows about schema validity and renderer failure. `/image/fromQuestion` is the only path that produces a typed "UnsupportedRequest" 400.

### Q3 — When the service fails partway through (planner / solver / layout), what should the caller see?

Today's failure mapping on `/image/fromQuestion`:

- **Planner exhausts retries (LLM cannot produce a scene that validates)** → HTTP status depends on the planner's typed error code: validation/derived-geometry exhaustion surfaces as a `500 InternalError` (the `AgentError.error_type` is the planner's, but the status mapping only carves out `UnsupportedRequest`/`InvalidScene` → 400 and `NotImplemented` → 501; everything else → 500). The body's `message` includes the underlying planner text such as `"Scene validation failed after N attempts"` or `"Generated scene failed validation after N attempts"`.
- **Renderer rejects an unknown component** → still `500 InternalError` over the wire (`UnknownComponent` is not in the special-cased list), with `details: {"component_type": "<name>"}`.
- **Any other renderer exception (e.g. layout could not place labels cleanly)** → `500 InternalError` with `error: "SVGGenerationFailed"` and the underlying exception text in `message`.
- **The user-facing body** is **not** a generic "could not render" — the underlying exception or planner message is exposed verbatim in the `message`/`details` fields. There is no curated, human-friendly mapping of "planner-retry-exhausted" vs "solver-could-not-converge" vs "label-overlap" — those distinctions only exist as raw error strings if at all.
- **Retry budget today**: the planner runs up to **3 total attempts** (`max_retries = 2` plus the initial try). The fallback service uses the same default (`max_retries = 2 → 3 total tries`). There is no separate solver/optimizer retry layer in the current pipeline.
- **Partial / fallback SVG?**
  No. The legacy `AgentService` has the LLM fallback **deliberately removed**. When the deterministic pipeline cannot produce an SVG, the caller gets an error response — never a placeholder image, never a "render failed" stub SVG.

I cannot answer what the *new* product should do — the legacy contract is: hard fail with HTTP 500 (or 400 / 501 for the typed subset) and surface the underlying error text.

What I cannot answer from code alone:

The factual answer is: the legacy service can render all of the names above. The split into v0 vs follow-up is a product call, not a code-derivable rule.

### Q5 — How is the 30-scene LLM eval that gates the planner work curated and scored?

I cannot answer this from the legacy code. The current service has no "30-scene eval gate" — there is no fixed eval-set runner, no gating threshold persisted in code, no record of who signs off, and no curation rule for how inputs are sourced. This is a new-product process question with no existing analogue to report on.

What I *can* say about today's planner behaviour, in case it informs the threshold decision:

- The planner's first-attempt outcome is observable per request (it logs attempt counts and emits Langfuse traces), but no aggregate "first-try success %" metric is computed or exposed.
- "Success" inside the current pipeline means the LLM's output validates against `SceneV1` *and* passes derived-geometry resolution. The renderer running successfully end-to-end is a separate, downstream check.

### Q6 — Must SVG output be visually equivalent to today's svg-gen, or are visual changes allowed?

This is a forward-looking product decision. From the code today the observable facts are:

- **Default trim padding** around a rendered scene is **14 units** (`SVG_TRIM_PADDING = 14.0`) applied symmetrically: the viewBox is recomputed as `(x − padding, y − padding, width + 2·padding, height + 2·padding)`. Callers cannot override this on the HTTP path — there is no `padding` query/body parameter on `/render` or `/image/fromQuestion`.
- Container-level layout padding constants are also fixed: `LABEL_SLOT_PADDING = 5.0`, `TOP_ALIGNED_BOTTOM_PADDING = 10.0`, container `_TOP_PADDING` / `_SIDE_PADDING = 20.0`.
- The service does not document a contractual stroke colour, font, or label size as part of its user-visible behaviour; those are renderer internals. Callers consume `image/svg+xml` content and do not negotiate styling.
- There is no "pixel-equivalence" guarantee or fixture-comparison endpoint exposed to callers today.

Whether the rebuild must be pixel-equivalent, whether specific style elements are load-bearing for downstream consumers, and what default padding upstream callers expect are all questions the code cannot answer — they require sign-off from the consumers of `/image/fromQuestion`.

### Q7 — What end-to-end latency budgets do callers expect for `/render` and `/image/fromQuestion`?

I cannot answer this from the legacy code. The service:

- Does not enforce a per-request timeout on `/render` or `/image/fromQuestion` at the HTTP layer.
- Does not publish or compute a p95 / p99 SLO.
- Does record per-request duration via the `X-Duration-Ms` response header on `/image/fromQuestion`, but does not gate on it.
- Has no caller-side timeout contract baked into the service.

What can be said about the work the service does today:

- `/render` does not call an LLM — it is pure deterministic rendering of a supplied `SceneV1`.
- `/image/fromQuestion` always runs the feasibility-check LLM and (if feasible) the planner LLM, with up to 3 planner attempts on validation/geometry failures.

The acceptable wall-clock budget for the new service is a product/consumer decision and is not represented in code.

### Q8 — When `/image/fromQuestion` cannot produce a diagram, what should the upstream pipeline see?

Today's `/image/fromQuestion` behaviour when no diagram can be produced:

- **Feasibility says "not renderable"** → HTTP **400** with body `{"detail": {"error": "UnsupportedRequest", "message": "Request is not supported by the deterministic SVG renderer. Fallback image generation is disabled.", "details": {"feasibility_reasoning": "<LLM text>"}}}`. No empty SVG, no JSON sentinel like `{"image": null}`, no placeholder image — the response is an error, not a "soft no".
- **Planner / renderer fail at runtime** → HTTP **500** (or **501** for the specific `NotImplemented` agent-error type) with `{"detail": {"error": "<ErrorType>", "message": "<underlying text>", "details": {...}}}`. The body **shape is the same** as the feasibility-rejection case (both use FastAPI's `HTTPException` envelope with the same `error`/`message`/`details` keys); only the **status code and `error` discriminator differ**.
- **Distinct cases visible to the caller**: the `error` field carries the discriminator — `UnsupportedRequest` (feasibility), `InvalidScene` (schema), `FeasibilityCheckFailed` (LLM call exploded), `UnknownComponent`, `SVGGenerationFailed`, `NotImplemented`, `InternalError`. So the upstream pipeline can branch on `error` rather than on status code alone.
- **Does the legacy service ever serve a question without a diagram?**
  Not at this boundary. `/image/fromQuestion` will not return success with no image — the success contract is always a real SVG or PNG body with a 200 status. "Skip the diagram and serve the question anyway" is a decision the *upstream* pipeline must make on its own when it sees the 400/500; the svg-gen service itself does not offer a partial-success mode.

What the new product *should* return when no diagram is possible is a product call — the legacy answer is: surface a typed HTTP error and let the caller decide whether to drop the diagram or fail the question.
